## Substantive documented provider gap

Official GitHub REST workflow API (version **2026-03-10**) returns **HTTP 200** with `workflow_run_id`, `run_url`, and `html_url` for workflow dispatch. [GitHub's 2026-02-19 changelog](https://github.blog/changelog/2026-02-19-workflow-dispatch-api-now-returns-run-ids/) also documents `return_run_details:true` for the older API (when absent, the older API can return HTTP 204 with no run identity). [GitHub REST docs](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event) require Actions:Write and a workflow configured for dispatch. Both provider paths remain disallowed unless the existing ingestion controller authorizes its own default-branch workflow change and validates an exact GitHub App installation/token grant.

**v16 material false-completion demonstrated:** An otherwise valid-looking `CONFIRMED` row containing a successful workflow run with matching repo/workflow/ref/head SHA and `controller_correlation` could pass `causalProofValid` even when the original controller reservation never captured the run ID returned by **this specific dispatch POST**. A successful *different* dispatch on the same ref/SHA could be misattributed. The prior code would report `state:complete`. The v17 test reproduces this with the actual unmodified v16 source.
