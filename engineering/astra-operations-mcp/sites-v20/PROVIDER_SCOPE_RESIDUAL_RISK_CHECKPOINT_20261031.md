## NEW MATERIAL provider-grant capability limits — official documentation

**Render**, [Scoped API Keys documentation](https://render.com/docs/scoped-api-keys), [launch (27 October 2026)](https://render.com/blog/scoped-api-keys-private-beta):
1. Scoped keys are still **early access/private beta**, single-workspace keys; actual account enrollment and effective rights are **unknown**. The creator's workspace role limits rights; revocation takes effect immediately; key scopes are mutable. Classic keys persist and must not silently substitute for scoped keys.
2. Under **Services**, the documented `Read & write` permission **also** permits creating and **deleting** services, not just changing `autoDeployTrigger`. A Render service-configuration PATCH-only or exact-service-only provider grant is **not established by these tables**. Even if a controller constrains the outbound JSON to `{"autoDeployTrigger":"off"}`, that application-layer guard does not reduce the provider credential's authority. Material residual deletion/create privilege must be separately risk-assessed before requesting an action-time key grant.
3. The documented **environment variables and secret files** permission allows **viewing secret values** at `Read`; separately documented **environment groups** `Read` explicitly permits **viewing groups and their secret values**. Never treat an environment-group Read key as metadata-only; owner must supply a genuinely redacted inventory/status facade without transmitting secret values. Owner cannot prove collision absence through a blind service env-var list.
4. Under **Deploys**, documented `Run` permission permits triggering deployments, **cancelling** them and triggering **rollbacks**. It is not a deploy-one-specific-revision-only provider grant. Do not couple routine configuration-PATCH admission with Deploy Run unless an explicit controller-owned deploy operation, side-effect inventory and release exist.

**GitHub**, [workflow REST permissions](https://docs.github.com/en/rest/actions/workflows), [installation-token narrowing](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation):
1. GitHub's repository `Actions: write` permission covers workflow dispatch **and** enabling/disabling workflows, so it is **not** a provider-enforced dispatch-only permission. A controller allowlist and exact original dispatch/run/first-attempt settlement reduce *application-level* risk but cannot be represented as a smaller GitHub provider privilege.
2. An installation token can be narrowed to exactly the named repository and permission set at issuance, expires after one hour, and cannot exceed installed-app grants. Such narrowing **does not restrict Actions:write to this one workflow**. Actual App ID/installation, granted effective permissions, secure destination and revocation mechanism remain unknown; no token was minted.
3. `workflow_dispatch` must appear in the workflow on the **default branch**, and a target branch/ref is separately specified. No change is authorised here; ingestion owner alone decides after its repair/release gate.
