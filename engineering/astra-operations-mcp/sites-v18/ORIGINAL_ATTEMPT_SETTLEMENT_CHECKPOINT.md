## Newly proved material v17 defect and v18 correction
Official [GitHub Actions contexts reference](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts) states `run_id` does not change on re-run, whereas `run_attempt` begins at 1 and increments. [GitHub's re-run reference](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs) says re-runs retain the original `GITHUB_SHA` and `GITHUB_REF` and the original triggering actor's privileges. A different actor can re-run the same workflow run and convert an originally unsuccessful attempt into a later completed/successful attempt with identical run ID, SHA and ref.

V17 accepted `Number.isSafeInteger(c.run_attempt) && c.run_attempt>=1` and could therefore project **`complete`** for such an unrelated later attempt, despite its original owner-pinned GitHub POST run ID binding. The v18 source requires **`run_attempt === 1`** for causal successful settlement. Later attempts are held with **no replay**. A separate future owner-approved re-run reconciliation contract would be necessary for legitimate later-attempt settlement. The v17 false-positive was reproduced with synthetic fixtures and corrected in v18; no provider access or credential was used.
