## Material documented defect
GitHub's published Actions contexts contract states `github.run_id` **does not change on re-run** while `github.run_attempt` begins at `1` and increments with each re-run. Its re-run documentation also states re-runs use the original `GITHUB_SHA` and `GITHUB_REF`, even when another actor triggers the re-run. Sources: https://docs.github.com/en/actions/reference/workflows-and-actions/contexts and https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs .

Version v17 correctly binds the controller-captured original dispatch HTTP 200 `workflow_run_id`, exact repo/workflow/ref, original pinned SHA, and immutable owner operation/change/revision. **However**, its `causalProofValid` accepted any `run_attempt >= 1`. A manually re-run failed attempt can therefore carry **the same run ID/ref/SHA** and `status:'completed', conclusion:'success', run_attempt:2`, causing v17 to project `complete` for the original dispatch without proving original attempt 1 succeeded. This is a material false-success/attribution defect; users could mistake unrelated manual remediation for the approved dispatch's original result.
